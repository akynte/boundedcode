# BoundedCode v0.1.0-alpha.1

**Bounded context. Bounded cost. Unbounded codebases.**

BoundedCode is a local-first AI software-engineering platform for working
on large repositories. It keeps model context bounded, persists task state,
verifies changes with behavioural evidence and escalates to a frontier model
only when needed (optional).

This is the first **public alpha**: usable, validated on a small held-out
sample (tasks not used during development and never shown to the agent),
tested on one machine with one model. Commands and
configuration may change. It is not production-ready.

## Highlights

- **Local inference:** llama.cpp (`llama-server`, supervised), with model
  profiles measured on the reference machine. Validated with
  Qwen3.6-35B-A3B (UD-Q4_K_M).
- **Long-running tasks:** a persistent task ledger and audit log. A task
  resumes after Ctrl-C, a crash or a reboot.
- **Compact context:** small task-specific context packs. Retrieval seeds are
  ranked so that quoted error messages lead to their origin. Context use was
  roughly 18–35 K tokens per task across repositories of 0.12–1.83 M
  estimated source tokens (bytes × 10/32): at most about 1.6 % of the largest
  repository and 29.1 % of the smallest (gin). The figures include all tool
  output, so they are upper bounds.
- **Repository intelligence:**
  - codebase-memory-mcp for breadth (graph, impact);
  - optional Serena v1.7.0 (MIT, pinned) for semantic depth;
  - cross-service contract analysis (HTTP, topics, env, Terraform).
- **Behavioural verification:** a task is `TASK_VERIFIED` only when a test it
  adds fails on the base commit and passes with the change. Otherwise it is
  reported as `tests_green` / UNVERIFIED.
- **Isolation:** each task works on a git worktree branch `agent/<id>`.
  Nothing is pushed or merged.
- **Sandbox:** agent tools run in a network-less container, with secret
  masking, protected paths, a deterministic command policy and hardened git
  handling.
- **Runaway control:**
  - per-response caps on thinking and visible output;
  - a progress-aware strategy budget;
  - stopped strategies are recorded and not repeated.
- **Task contract:** required behaviour, allowed alternatives and material
  ambiguity are surfaced before implementation (`task run --clarify`).
- **Optional frontier escalation:** a Z1-Z4 policy via the Codex CLI with a
  ChatGPT sign-in, or manual packets. API keys are refused, and packets are
  sanitized. Enabled but not triggered in the second validation; in the
  first, 4 frontier calls were sent and no task was accepted.

## Validation

**Initial validation:** 0/8, then 1/8 after the first defect fixes
([report](https://github.com/akynte/boundedcode/blob/main/docs/benchmarks/small-real-world-validation-2026-10.md)).
Those failures drove the engineering work. Development reruns are not
counted as validation.

**Second validation (held out):** 6 public tasks not used during development
and never shown to the agent, from the SWE-bench Multilingual and
Multi-SWE-bench benchmark datasets. They were screened before
execution for consistency between each issue and its acceptance test, frozen,
then run once each:

- 5 of 6 strict `TASK_VERIFIED` successes, also passing the datasets'
  hidden acceptance tests (hidden from the agent)
- 6 of 6 hidden acceptance tests passed
- all five strict successes local-only: no frontier calls (escalation
  enabled, not triggered)
- 0 false verification passes among the 5 `TASK_VERIFIED` tasks, on a set
  screened for issue-derivable tests (in development runs with the same gate
  design, tasks were `TASK_VERIFIED` but failed hidden tests; see the report)
- 0 human code intervention

The first and second validations used different screening, so 0/8 → 5/6 is
not an improvement curve; see the report.

The sixth task (Prometheus) was implemented correctly, but the evidence
checker did not link its data-driven test file to the test that reads it.
It is therefore scored as a strict failure.

Small validation sample; not a statistically comprehensive evaluation.
[Full report](https://github.com/akynte/boundedcode/blob/main/docs/benchmarks/second-independent-validation-2026-10.md).

## Known limitations

1. Small validation sample (8 + 6 tasks, one run each). It covers one
   machine and one model.
2. Ambiguity detection is model-derived and has false positives. The second
   validation ran with `task.ambiguity: proceed`; under the default `ask`,
   one clear task (vue) would have stopped on a false ambiguity flag.
3. Behavioural evidence misses data-driven test files consumed by a test
   elsewhere.
4. Frontier escalation was enabled but not triggered in the second
   validation; in the first, 4 frontier calls were sent and no task was
   accepted.
5. The strategy governor has not yet stopped a live runaway; it is
   calibrated on development runs.

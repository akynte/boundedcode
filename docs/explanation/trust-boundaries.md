# Trust boundaries

BoundedCode treats model output and repository text as untrusted inputs.
The trusted Go supervisor chooses which structured requests to execute and which
evidence is required. This is a set of controls, not a proof that an agent cannot
cause harm.

## Operator, model and supervisor

The operator trusts the BoundedCode binary, inference runtime, configuration,
toolchain and verification commands. Review a repository's build scripts and
`.agent/verify.toml` before running it: a test command can execute arbitrary
repository code.

The native engine exposes [ten scoped tools](../reference/tool-schemas.md), not
a general shell. Go file tools check paths, symlinks, protected files and the
plan's write grant. These tools execute in the trusted supervisor process;
the model is not itself an isolated process making filesystem calls.

Repository content is delimited with per-run trust markers and marker-shaped
text is neutralized. This helps distinguish data from instructions; it does not
make prompt injection impossible. A persuaded model can still propose an unsafe
but schema-valid edit. The firewall, diff checks, verification and human gate
must stand independently of prompt wording.

## Native tasks and editor sessions are different

Native `bcode task run` edits a separate Git worktree. Finalization checks the
candidate and, with the default apply gate enabled, asks for approval before
committing on `bc/task/<task-id>`. It does **not** merge that branch into the
original checkout. Verification commands run in a disposable snapshot (base commit plus the
task's diff) and cannot modify the task worktree; the snapshot itself is
writable, not immutable. See [verification](verification.md).

The optional MCP/OpenCode tools can edit the opened checkout. Running
`bcode opencode setup` configures tools and instructions; it does not confine
OpenCode's own tools. `bcode opencode run` is a separate, explicit launch path.
An MCP completion verdict cannot retroactively isolate edits already made by
the editor. See [OpenCode](../how-to/use-with-opencode.md).

## Processes and network

Builds, tests and generators run through `internal/sandbox`. Protection depends
on the available Linux mechanisms and deployment. A host install has no outer
Docker boundary. Container mounts, UID, capabilities and network configuration
remain operator responsibilities.

Landlock filesystem rules and optional bubblewrap namespaces restrict child
processes. Landlock TCP rules are port-based, ABI-dependent and do not cover all
network protocols, including MPTCP. Granting the inference port grants access to
that port, not only to safe HTTP routes. The runtime does not provide an
HTTP-method/path filter for model-management endpoints.

Verification can need dynamically allocated local test ports. The ephemeral-port
allowance is wider than a single disposable service; unrelated services in that
range may be reachable. Explicitly denied BoundedCode service ports do not
turn that range into a general loopback firewall.

There is no configuration flag that makes BoundedCode offline, because the
decision plane is required and the honest answer is that the system has a
network dependency. Nothing here is a kernel-level network kill switch, and the
shipped Docker bridge is not a deny-all network. For sensitive or untrusted repositories,
use a deliberately restricted container/VM network and review mounts. See
[isolation](isolation-model.md).

## Subprocess execution

The evaluation tooling shells out to `git`, `docker`, `python` and `cp`. What
matters for trust is not that a variable appears in an `exec` call but where
that variable came from.

| Value | Origin | Can the model or the network influence it? |
|---|---|---|
| The executable | A string literal — `"git"`, `"docker"`, `"cp"` — resolved through `PATH` | No |
| Container ids | Generated by the Docker daemon moments earlier | No |
| Image references, image dirs | The frozen suite manifest, committed and hash-pinned | No |
| Run roots and workspace paths | Operator configuration | No |
| `git` subcommand arguments | Fixed string constants at each call site | No |

No path uses a shell. `exec.CommandContext` passes argv directly to `execve`,
so no element is word-split, globbed or interpreted. Two `gosec` G204 findings
remain marked at the line with exactly this reasoning rather than suppressed
for the package; the marking records the trace, it does not replace it.

The task path is different and stricter: the native agent has **no shell tool
at all**, and its file access goes through the write firewall rather than
through a subprocess.

Evaluation writes that leave the package's own directory tree are resolved and
checked against the run root before execution — see
[containment](reliability.md#filesystem-containment-for-evaluation-writes).
That is a check on specific writes, not a general filesystem sandbox.

## Data and credentials

Workspace databases, cache keys and retrieval provenance are scoped and tested.
This is an application boundary, not OS isolation between mutually hostile
processes running under the same user. Persisted prompts, artifacts, diffs,
judgment metadata and test output may contain sensitive repository information.
Protect the data directory and backups accordingly.

Keep credentials in environment variables named by configuration, not committed
YAML. Tool environment scrubbing and sensitive-path/credential checks reduce
exposure; they are not universal secret detection.

The required [Jev service](judgments.md) sends selected state to TypeSafe.
Strict mode excludes repository-source fields but still sends objectives,
paths and symbols; an objective can itself contain sensitive text.

The HTTP API has no authentication. Keep it on loopback and do not expose it to
an untrusted network. Read-only status and artifact endpoints can still disclose
repository information.

## Completion is bounded, not infallible

The model's `done` call cannot override failed checks or a denied gate. The
fresh-context model reviewer can request more work, but cannot make a failed
deterministic check pass. Passing tests still does not prove the task is correct,
the tests are adequate, or the implementation is secure. Historical evaluations
include false acceptance.

Report suspected boundary violations through [the security policy](https://github.com/akynte/boundedcode/blob/main/SECURITY.md).

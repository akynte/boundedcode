# Harness laboratory: first record (2026-10-30)

Phase 11 built an offline laboratory for testing changes to BoundedCode's
own harness ([usage](../usage/lab.md)). This record covers four things:
- the published methods it studied;
- what it found in the recorded runs;
- what it says about decisions made by hand in earlier phases;
- its first prospective experiment.

Machine, model and server are those of the
[cross-language evaluation](cross-language-2026-10.md): Qwen3.6-35B-A3B
(UD-Q4_K_M, sha256 `ac0e2c1189e0…`), llama.cpp b11146, one RTX 4060 laptop.

## Summary

- **The laboratory does not improve BoundedCode by itself.** It analyses
  runs, tests pre-registered changes in isolation, and writes proposals.
  - A person approves and promotes a configuration change.
  - Code changes are landed by ordinary review.
  - Its detectors and its catalog of interventions are fixed code. The
    code candidate tested here was written by hand.
- **Most direct-mode failures are weak verification.** In 1,523 recorded
  development runs, 103 failures were runs whose own tests passed while
  the hidden checks failed (87 in direct mode, 16 bounded false passes).
  - No tunable can address this: post-change checks are verification, and
    deliberately out of every experiment's reach.
  - It becomes a code hypothesis (`verify-examples`), not yet written.
- **Two other patterns are associated with failure beyond chance:**
  - context excess: 19% of runs with it fail, against 7%;
  - rerunning a test with nothing changed: 2 of 4 runs fail, against 8%.

  Both are almost all in Go development tasks, which is most of the
  development set. That is the reason the decisions check every language
  separately.
- **None of seven past decisions holds up on its own data.**
  - Re-read with a paired test, five are inconclusive. They rest on two
    trials of 23–26 development tasks with success near 90–98%: too few
    tasks differed for any test to tell.
  - MTP is clearly faster (23 tasks faster, 3 slower, ×0.83 per task) but
    is rejected for 24% more processed tokens per success. The Phase 09
    write-up did not report that cost.
  - n-gram speculation was slower on 16 tasks and faster on 7, but by less
    than the 15% the rule needs.
- **The first prospective experiment found nothing to promote**
  ([results](#the-first-prospective-experiment)). It tested two hypotheses
  from the analysis against the committed production code.
  - Every arm is inconclusive, and no proposal was written.
  - The loop guard made its own target task fail in both trials, where
    every other arm passed it.

## Methods studied

Each method was checked against its primary source: arXiv full text and the
repository's own LICENSE file, on 2026-10-30. Five citations were re-checked
against their arXiv abstracts. All the released code is Python research
code.

| Method | What we took | Code and licence | Why not more |
|---|---|---|---|
| Agentic Harness Engineering (Lin et al., arXiv 2604.25850) | <ul><li>A file-level, revertible representation of each change</li><li>Evidence distilled from trajectories</li><li>Each change states what it should fix and what it puts at risk (our `predicts`), checked after the run</li></ul> | MIT | <ul><li>An unattended evolution loop driven by GPT-5.4</li><li>Evaluated on the benchmark it searched</li><li>Its own regression predictions were only about twice as good as chance, so we catch regressions empirically</li></ul> |
| Meta-Harness (Lee et al., arXiv 2603.28052) | <ul><li>Every candidate's code, traces and scores kept as files</li><li>Selection against context cost</li><li>Separate search and test sets</li></ul> | Framework MIT; the optimised harness has no licence file (not reusable) | Search and final evaluation on the same 89-task benchmark |
| RRSI (Xia et al., arXiv 2609.24972) | <ul><li>An edit budget (one isolated change per arm)</li><li>Refusing benchmark-specific changes (our leakage check)</li><li>Promoting only on results outside the tuning set</li></ul> | Apache-2.0 | Its abstract reports in-distribution gains of harness evolution that "shrink or even vanish" out of distribution: the reason held-out tasks decide here |
| Self-improving agents: SICA, Darwin Gödel Machine, Gödel Agent, ADAS, STOP, AI Scientist, Live-SWE-agent | The documented failure cases, as boundaries | Various | Rejected as architectures. All depend on frontier models, cost USD 300 (ADAS) to 22,000 (Darwin Gödel Machine) per run, and report optimisers editing their own checks:<ul><li>removing the logging a hallucination check used</li><li>turning a sandbox off</li><li>extending their own time limit</li></ul> |
| The Complexity Trap (Lindenbauer et al., arXiv 2508.21433) | Masking old observations matched summarising at about half the cost: the `observation-masking` hypothesis | MIT | Not assumed to hold for this model: a hypothesis to test |
| Budget Tracker (Liu et al., arXiv 2511.17006) | Showing the agent its remaining budget: the `budget-notice` hypothesis | Apache-2.0 | One model in its coding result: to replicate here |
| Trajectory studies, MAST, TRAIL, Who&When | Cheap deterministic signals first: <ul><li>run length</li><li>repeated calls</li><li>early errors</li></ul> | MIT (datasets) | Automated failure attribution is weak: step accuracy 14% in Who&When, 11% for the best model on TRAIL. Our detectors are deterministic, and their associations are reported as associations |
| Test-time compute (CodeMonkeys, S*, SWE-Search) | Selection by execution matters more than wider search | Various | Tree search multiplies cost (SWE-Search: USD 40.86 to 576.00 for GPT-4o); not for a local GPU |

The table summarises a fuller audit (37 papers and 31 repositories), which
is not committed: design notes are not kept in the repository. Its figures
quoted here come from the papers' own text.

## What the recorded runs show

The analysis covered every direct-mode and bounded-mode report from
2026-10-27 to 2026-10-30: 116 reports and 1,523 development runs.
- 114 held-out runs and 96 skipped runs were left out.
- Tool calls were read from the transcripts of all 1,351 direct-mode runs.
- Inputs: `benchmarks/lab/analysis/20261030-analysis.{json,md}`.

| Pattern | Runs (of eligible) | Tasks | Failures it explains | Fail with / without | Wasted calls | Associated with failure |
|---|---|---|---|---|---|---|
| weak verification | 117 (1108) | 15 | **103** (87 false confidence, 16 bounded false passes) | 21% / 10% | – | no |
| context excess | 26 (1351) | 3 | – | **19% / 7%** | 183 | **yes** |
| unnecessary retries | 21 (1523) | 6 | 17 (attempts all failed) | **50% / 8%** | 27 | **yes** |
| ineffective compaction | 7 (1351) | 1 | – | 43% / 7% | 84 | yes (one task) |
| repeated calls | 19 (1351) | 2 | – | 16% / 7% | 199 | no |
| tool misuse | 38 (1351) | 10 | – | 5% / 7% | 84 | no |
| retrieval miss | 0 (12) | 0 | – | – | – | – |
| escalation | 0 (172) | 0 | – | – | – | – |
| budget exhausted | 0 (1133) | 0 | – | – | – | – |

Notes on the table:
- **Retrieval misses could be checked in 12 runs only.** The analysis needs
  the files a task is about, which a task states only when it has a
  reference solution or an expected path. Most of those tasks are held out.
- **No bounded run escalated:** none had a frontier model configured.
- **The budget pattern and the looping `sec-mcp-ticket` runs** seen in
  Phase 10 are in held-out tasks. The analysis therefore leaves them out,
  which is what keeps those tasks independent.
- **Most patterns are Go's** because most development tasks are Go: 104 of
  117 weak-verification runs, and all 26 context-excess runs.
- **One task carries several patterns.** `session-x-tools` read the same
  file 80 times in one run, and re-read three unchanged files after a
  compaction.

The hypotheses drawn from this are in
`benchmarks/lab/analysis/20261030-hypotheses.md`, and their draft
experiments in `benchmarks/lab/drafts/`. In order of evidence:

1. `verify-examples` (code): run the request's own examples before
   reporting a change done.
2. `observation-budget`: prune command output to 4 KB; it must beat cutting
   tool results at 8 KB.
3. `working-set-24k`.
4. `rerun-note` (code).
5. `fewer-attempts`.
6. `working-set-48k`.
7. `observation-masking` (code).
8. `tool-hints` (code).
9. `loop-guard` (code).

## Past decisions, re-read

Each earlier phase decided on two trials of the development suite.
`lab evaluate` re-read those runs with `decide_on: dev`, so none of the
verdicts can become a proposal. The files are
`benchmarks/lab/retrospective/*.yaml` and their decisions.

| Decision then | Metric | Paired over tasks | Laboratory verdict |
|---|---|---|---|
| Phase 05: adopt adaptive retrieval (44/46 against 41/46) | success | 3 better, 1 worse, 19 tied (p = 0.31) | inconclusive |
| Phase 06: reasoning history `auto` (−16% prefill) | median seconds | 12 better, 10 worse (×0.97, p = 0.42) | inconclusive |
| Phase 07: structured compaction and pruning (25/26 twice against 23 and 24) | success | 3 better, 0 worse (p = 0.13) | inconclusive |
| Phase 08: concurrent read-only calls (microbenchmark gain) | median seconds | 11 better, 11 worse (×0.95) | inconclusive |
| Phase 09: keep routing off (change tasks 18/22 against 21/22) | success | 0 better, 2 worse (p = 0.25) | inconclusive |
| Phase 09: reject n-gram speculation (40.9 s against 37.1 s) | median seconds | 7 better, 16 worse (×1.03, p = 0.047) | inconclusive: slower, by less than the 15% the rule needs |
| Phase 09: MTP kept as an experimental profile (−14% task time) | median seconds | **23 better, 3 worse (×0.83, p < 0.001)** | **reject**: 24% more processed tokens per success, beyond the policy's tolerance |

**How to read it.** A sign test needs at least five tasks to differ, all
the same way. With success at 90–98% on 23–26 tasks, a change in success
moves two to four tasks: no success claim of those phases was measurable on
their own data. The point estimates may still have been right. The data
cannot say.

**On MTP:** with it, a run used 22% more uncached prompt tokens (3,920
against 3,203) and 15% more prompt overall. That is real prefill work, and
time fell anyway because decoding was 42% faster. Two trials cannot tell
whether MTP causes the longer trajectories or the runs differed by chance.
The profile stays experimental, as Phase 09 left it.

**What it means for the suite:** to decide success on this model, the
suite needs harder tasks (more failing runs to move) or more of them.
Speed and token metrics, which move on every task, are decidable now.

## The first prospective experiment

Experiment `p11-context-and-loops` was written before it ran
(`benchmarks/lab/experiments/p11-context-and-loops.yaml`). The run:
- five arms, two trials each, interleaved, from 08:38 to 13:23 on 2026-10-30;
- 20 held-out tasks in seven languages and 6 development tasks;
- every arm built from revision `15ab3aa`, the committed production code.

The evidence is in `benchmarks/lab/experiments/p11-context-and-loops/`, and
`bcode lab evaluate` on that directory checks every report's hash and
reproduces the decision byte for byte.

| Arm | Change | Held-out success | Development success | Primary metric (held-out, per task) | Paired over tasks | Verdict |
|---|---|---|---|---|---|---|
| baseline | none | 38/40 | 16/16 | – | – | – |
| max-tool-output-8k (simpler) | tool results cut at 8 KB | 35/40 | 15/16 | tokens per success 4,617 → 4,540 | 6 better, 7 worse | inconclusive |
| observation-4k (candidate) | command output pruned to 4 KB | 37/40 | 13/16 | tokens per success 4,617 → 4,134 | 7 better, 6 worse | inconclusive |
| max-turns-40 (simpler) | turn limit 40 | 37/40 | 15/16 | model calls per run 7.5 → 6.8 | 4 better, 5 worse | inconclusive |
| loop-guard (candidate) | patch: the third identical call refused | 33/40 | 15/16 | model calls per run 7.5 → 8.3 | 8 better, 5 worse | inconclusive |

No arm had a security failure, a false acceptance or a false rejection.

**Pruning command output to 4 KB.** Prompt tokens per run fell 20% on
average (68,223 to 54,850). That is not a measured effect:
- Per task it is a coin toss: 7 better, 6 worse.
- The mean fell because two large mixed-language tasks used fewer tokens.
  On those tasks the baseline itself varied twofold between its two trials
  (194,000 and 375,000 prompt tokens on `poly-generated-client`).
- The saving followed the number of model calls more than the size of tool
  output, and the plain 8 KB cut saved on one of the two tasks too.
- Development success fell from 16/16 to 13/16. Three runs is too few to
  call a regression.

**The loop guard made its target task worse.** It was predicted to fix
`sec-mcp-ticket`. Every other arm passed that task in both trials (8 of 8);
with the guard it failed both.
- In one message the model asked for the same `todo_write` call 90 times,
  and each refusal went back into its context. The refusals did not stop
  the repetition.
- Trial 1 ran 80 model calls. Trial 2 ended with a server error parsing the
  model's next tool call.
- The guard refused calls in only one other task (`session-x-tools`), which
  passed. The arm's other failures had no refusals.

Three parts of the laboratory each saw this differently:
- **The verdict says inconclusive**, correctly by its rule. The arm's
  metric is model calls per task, and one task cannot move a sign test.
- **The gate does not call it a regression.** It needs two tasks that pass
  in every baseline trial and fail in every candidate trial, and this is
  one.
- **The prediction check is where it shows.** As first written, it filed a
  predicted fix that got worse under "not fixed". The check now lists it as
  "worse instead", and the decision was taken again from the same hashed
  reports. `decision-at-run.json` keeps what the run decided; no verdict
  changed.

So the hypothesis that refusing repeats stops loops is contradicted on the
one task where loops were seen. A refusal is more context for a model that
is already repeating itself. A guard that ends the turn, or drops the
repeated calls without a reply, would be a different hypothesis.

**Turn limit 40.** It changed no task beyond chance (4 better, 5 worse).

**Per-language results.** The decision compares each language over its own
held-out tasks. Only Python has five or more, the fewest a sign test needs:
- Python: unchanged in every arm.
- The other six languages: inconclusive, with one to four tasks each.

As first written, the decision reported these as "unchanged" under a
"success" label. It now says "inconclusive" and names the metric. A
regression confined to one language other than Python could not have been
seen.

**Disclosure.** The loop-guard hypothesis was influenced by held-out
evidence. The analysis left held-out runs out. But I had seen
`sec-mcp-ticket` loop in the Phase 10 held-out results before writing
the hypothesis, and I named that task in its prediction. That arm's
result on `sec-mcp-ticket` is therefore not independent evidence. Had the
guard helped there, the result should not have counted for it. Against the
guard, it counts as much as any other single task.

## Limitations

- **One machine and one model.** A verdict is for this model on this
  hardware.
- **The suite is small.** About 20 held-out direct tasks in seven languages,
  and half of them Python. Rust, Java, PHP and Ruby change tasks cannot run
  on this host, so the held-out direct tasks do not cover them.
  - Python is the only language with enough held-out tasks for its own
    paired test. For the others, a per-language regression is visible only
    through the gate's rules, which need six runs per side.
  - With two trials, a single task that flips consistently is below the
    gate's threshold, as with the loop guard.
- **Predictions are checked on success only.** A predicted fix that was
  about tokens rather than passing, such as `session-x-tools` here, shows
  as "not fixed" whatever its tokens did.
- **The detectors are heuristics.**
  - A "shell command for a tool" may be legitimate.
  - A "verification command" is matched by words such as test, build and
    check.
  - A file "read again" may have changed outside the agent.

  They were checked on hand-built transcripts (`internal/lab` tests) and by
  reading their findings on real runs, not against labelled data.
- **Held-out independence depends on discipline.** The analysis leaves
  held-out runs out. But the person writing a hypothesis may have seen
  held-out results elsewhere, as here: see the experiment's disclosure.
- **A patched arm's harness code is not sandboxed.** Its agent's commands
  are, by the unchanged direct-mode sandbox. Tampering with reports, tasks
  or fixtures is detected by hashes, not prevented. Review a patch before
  running it.

# Acceptance judges — 2026-09-23

Raw data: [`2026-09-23-judges.json`](2026-09-23-judges.json). Reproduce with
`bcode eval judges --oracles evals/oracles` from the repository root.

## The question

A coding agent hands back a change. Does it solve the task? Two judges decide,
and each is scored against the task's hidden acceptance command:

- **ci** runs the repository's visible build, vet, test and format checks on the
  patched tree, the way a pipeline with required checks does.
- **bcode** runs the supervisor's completion contract on an indexed repository:
  the same checks, in a verification snapshot, plus the checks on the tests that
  reach the change.

Both run the same visible checks, so the difference is what the supervisor
adds. Neither judge is given a hidden oracle. The task's hidden tests are what
label each candidate, and judging with them would be circular.

## What it shows

**Without an oracle, the supervisor stops tampering with the visible tests. It
does not stop being wrong.**

- Every candidate that broke the code and then skipped or deleted the test that
  would catch it was accepted by `ci` and rejected by `bcode`. The rejection
  names the test, the declaration it reaches and what the change did to it.
- Every plausible-but-wrong fix was accepted by both. Nothing visible tests the
  behaviour they get wrong; only an oracle could.
- Every candidate that rewrote a test to expect the bug was accepted by both. The
  test still reaches the change and still passes.
- The one false reject is a correct fix that also skips an unrelated passing
  test reaching the changed code. The rule cannot tell that skip from the attack
  it exists to stop. That is the rule's cost, and it is shown here rather than
  tuned away.

**On real patches from a frontier agent, the checks that need no oracle made no
difference.** The agent never touched a test in the ways those checks guard
against. Its one real failure was a plausible regression in code no visible
test covers, which is exactly the class the hand-written candidates showed
neither judge can catch. The other failure is not an acceptance question at all:
the task's objective does not name the method the hidden test calls. That is a
defect in the task, reported here rather than fixed.

What would have caught the regression is a check that knows what the reconciler
is for: "an orphaned cancellation's stock is recovered". That is a hidden
acceptance check or an invariant written by someone who knows the system. It is
the oracle this benchmark cannot measure without circularity, and the evidence
here says it is where the value is.

Two grading fixes came out of this run. In both, the grader was failing the
code for something that was not the code's fault:

- The agent's own tests in `perishable-zone` and `restock-silence` shared names
  with hidden tests, so the package did not compile. When a hidden file collides
  with a candidate's test, the candidate's test files in that package are now
  returned to the fixture's and the hidden tests rerun.
- Restoring test files unconditionally broke `signature-change`, whose candidate
  had to update an existing test to the new signature. Restoring happens only on
  a collision.

## With an independently written oracle

The third judge, **bcode+oracle**, is the completion contract with a hidden
acceptance suite installed for each task. The suites were drafted by Claude Code
from each task's objective and unfixed code, without seeing the hidden tests
that label the candidates, and used without review.
[`evals/oracles/README.md`](https://github.com/akynte/boundedcode/blob/main/evals/oracles/README.md)
has how and what that does and does not make independent. $9.83 for all ten.
Every suite fails on the unfixed code.

| Candidates | ci false accepts | bcode false accepts | bcode+oracle false accepts | bcode+oracle false rejects |
|---|---|---|---|---|
| hand-written | 9 of 9 | 5 of 9 | **0 of 9** | 1 of 4 |
| agent patches | 2 of 2 | 2 of 2 | **1 of 2** | 0 of 8 |

- **It caught the real regression.** The agent's `reconcile-steals` patch was
  accepted by the other two judges. The drafted suite for the worker package
  included `TestOracleReconcileRecoversOrphanedReservation`, the behaviour the
  patch broke, and rejected it. The model was told only
  `hidden acceptance check authored-internal-worker did not pass`.
- **It caught every wrong or rewritten hand-written candidate**, the classes the
  checks without an oracle could not.
- **It rejected no correct work** except the same skip-rule case as before: all
  eight solved agent patches and both reference fixes were accepted.
- **The remaining false accept is the ambiguous task.** The oracle author chose
  the same method name as the patch agent, so it accepts that patch. A person
  specifying the change would have named the method, and the task should.

**This is the first evidence in this repository that the thesis can hold:** an
oracle drafted cheaply from a description, without the grading tests, caught
the failure a frontier agent actually produced, and rejected no correct agent
work. It is also evidence of where the value is. Every catch on real work came
from the oracle, none from the checks around it.

## What it does not show

- **The hand-written numbers are not rates.** One or two candidates per failure
  class, written to test each mechanism.
- **Ten agent patches are one run each.** Two failures cannot support a rate,
  and one agent on its own tasks says nothing about other agents or larger
  changes.
- **The oracle author and the patch agent are the same model.** They are not
  independent of each other, only of the labels. An oracle from another model
  or a person may agree less, or catch different things.
- **The drafts were not reviewed.** In use, a person would accept or edit them;
  that cost is not measured.
- Two tasks, one language, and the smallest fixtures in the set.
